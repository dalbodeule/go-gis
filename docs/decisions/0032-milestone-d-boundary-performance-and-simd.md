# ADR 0032: CSV 경계와 SHP 분리의 성능 경계 및 SIMD 판단

상태: Accepted — 2026-10-24

CSV 병합은 파일마다 열고 파싱한 뒤 즉시 닫는다. GUI는 선택 당시 파일 크기의 합을
확인하고 실제 읽은 바이트에도 16 MiB 한도를 적용한다. CSV 구문 오류는 행 진단으로
보고하되, 지속적인 파일 읽기 오류는 즉시 실패로 반환한다. Lua 필터·분리와 경계
분리는 프로젝트의 읽기 전용 렌더 스냅샷을 사용해 입력 도형 전체의 깊은 복사를
피한다.
백그라운드 공간 연산도 독립된 프로젝트 스냅샷에서 실행한 후 결과를 교체해,
화면이 원래 프로젝트를 읽는 동안 서비스 상태를 동시에 바꾸지 않도록 한다.

SHP 면 분리는 GEOS가 각 원본 도형을 한 번만 읽고, 경계 도형도 한 번씩 읽는다.
두 도형의 범위가 겹칠 때만 GEOS 교차 검사를 수행하고, 면이 아닌 교차 결과는
제외한다. 면과 접촉점·선이 섞인 결과에서는 면 성분을 보존한다. GUI의 20만 비교
한도는 전체 도형 쌍이 아니라 **범위가 겹치는 후보 쌍**에 적용한다. 따라서 서로
떨어진 경계가 많은 프로젝트는 이전보다 큰 입력도 처리할 수 있으며, 겹침이
지나치게 많은 입력은 계속 제한한다. CLI는 이 대화형 한도를 적용하지 않는다.

Apple M3 arm64에서 1,000개 면 × 32개 경계의 1회 측정은 변경 전 약 127.8ms,
19.4MB 할당이었고, 변경 후 약 9.6ms, 1.0MB 할당이었다. 다른 1회 측정에서는
19.4ms가 나왔으므로 시간 수치는 실행 환경에 따라 달라진다. 10,000개 면 ×
32개 경계는 약 93.1ms, 11.1MB 할당이었다. 10만 점의 경계 생성은 숫자 속성
직접 읽기 변경 후 약 39~40ms, 볼록 외곽선 정렬만 약 11.7ms였다. 교차곱 산술
10만 회는 약 0.07ms로 전체 처리의 작은 부분이다.

현재 데이터 흐름에는 별도 SIMD 분기를 두지 않는다. x86-64/AMD64에는 SSE·AVX,
ARM64에는 NEON이 해당하며 Apple Silicon은 ARM64 경로다. AMD64용 NEON 명령은
없다. 병목이 정렬·할당·파싱·GEOS 호출인 상황에서 별도 어셈블리와 CPU 기능별
분기는 유지 비용과 검증 범위만 늘린다. 공용 Go 명령과 Lua 패키지는 Linux
amd64/arm64 대상으로 교차 컴파일했고, 네이티브 패키징은 기존 OS·아키텍처 CI
매트릭스를 따른다. 이 문서의 수치는 Apple M3에서의 측정이며 다른 CPU의 실행
성능을 보장하지 않는다.

후속 측정에서는 CSV 텍스트의 U+FFFD 검사에 SIMD를 활용할 여지가 확인되었다.
기존 `strings.ContainsRune`은 UTF-8 유효성을 확인한 뒤 문자열을 글자 단위로
다시 순회했다. 먼저 `utf8.ValidString`으로 확인하고, 이후 U+FFFD의 첫 바이트를
`strings.IndexByte`로 찾아 나머지 바이트를 확인한다. Go 표준 라이브러리의
긴 문자열 바이트 검색은 ARM64에서 NEON, amd64에서 SSE/AVX2 경로를 사용하므로
프로젝트 전용 CPU 분기 없이 해당 최적화를 이용한다. 유효하지 않은 UTF-8과
실제 U+FFFD 거부 정책은 유지한다. 384바이트 입력칸 1개의 검색은 Apple M3에서
기존 글자 순회 약 217ns, 바이트 검색 약 15ns였다. 작은 입력칸에서는 SIMD
경로에 진입하지 않을 수 있다.

CSV 파서의 행 배열 재사용도 적용했다. 100만 행 가져오기 3회 측정은 변경 전
약 526ms·799MB·1,400만 할당, 변경 후 약 494~512ms·735MB·1,300만
할당이었다. 실행 시간 차이는 측정 잡음이 있으므로 메모리와 할당 감소를 더
확실한 효과로 본다. 경계가 32개에서 1,024개로 늘어난 1만 면 분리 측정은
약 79ms와 82ms로 비슷했다. 이 조건에서 도형 범위 비교에 별도 SIMD를 넣어도
전체 처리 시간 개선 폭은 작다.

Linux·Windows amd64에서의 실행 검증과 동일 머신 성능 비교 절차는
[amd64 검증 가이드](../testing/amd64-csv-simd-validation.md)를 따른다.

## 후속 측정: CSV 점과 볼록 외곽선 문자열 생성

CSV 점을 WKT로 만들 때 좌표마다 `FormatFloat`과 `Sprintf`로 문자열을 따로
할당하던 경로를 하나의 바이트 버퍼와 `AppendFloat`로 바꿨다. 텍스트 속성에는
필요 없는 공백 검사도 생략한다. 100만 행 가져오기 3회 측정은 Apple M3에서
변경 전 약 483ms·735MB·1,300만 할당, 변경 후 약 377~392ms·687MB·900만
할당이었다. WKT 표기 방식은 유지한다.

경계 그룹 값이 이미 문자열이면 `fmt.Sprint`를 두 번 호출하지 않고 그대로
사용한다. 10만 점·16개 그룹 계산에서 약 45ms·601,000할당이 약
38ms·401,000할당으로 줄었다. 모든 점이 외곽에 가까운 1만 점 측정에서는
폴리곤 WKT를 좌표별 임시 문자열 없이 버퍼에 작성해 약 5.65ms·70,000할당이
약 2.68ms·40,000할당으로 줄었다. 도형 형식과 시작점으로 돌아와 닫는
규칙은 유지한다. 시간 수치는 단일 머신의 짧은 반복 측정이며 일반 성능
보증으로 해석하지 않는다.
