# 읽기 전용 viewport 누적 payload 예산 확대

2026-10-04

세종시 연속지적도·지적도근점·건물 레이어를 함께 표시할 때 화면 레이블이 약 500개로 제한되어 있어도 `visible read-only data exceeds the 32 MiB geometry/property budget` 오류가 발생했다. 이 예산은 레이블 개수 제한이 아니라, 현재 viewport에 남아 있는 읽기 전용 피처의 지오메트리·속성·레이블 payload 추정치 합계에 적용된다. 화면 레이블을 더 숨겨도 원본 피처의 지오메트리·속성 보유량은 크게 줄지 않는다.

읽기 전용 viewport 전체의 누적 payload 상한을 32 MiB에서 64 MiB, 128 MiB로 단계적으로 늘렸다. 이후 50,000피처 상한 때문에 336개 공간창 중 299개 처리 후 렌더링이 중단된 사례가 있어 viewport의 피처 상한을 100,000개로 확대했다. 그 상한에도 가끔 닿아 피처 수 상한을 300,000개, viewport payload를 256 MiB로 늘린다. 개별 공간창의 32 MiB/20,000 피처와 동시 작업 수는 유지한다. 누적 payload 검사에서는 덧셈 overflow를 피하도록 남은 예산과 추가량을 비교한다.

대축척 실자료에서는 피처·byte 예산보다 8 Mi 정점 배치 한도가 먼저 소진됐다. 따라서 source 배치 한도를 12 Mi 정점, Qt scenegraph 상한을 36 Mi 정점으로 함께 확대한다. 화면상의 semantic LOD 2–4에서는 32점 이상인 선·폴리곤만 GEOS topology-preserving 단순화를 적용한다. 개별 폴리곤 형상은 유지하지만 인접 필지 간 경계가 픽셀 단위로 완전히 일치한다는 보장은 없으며, 확대하면 원본 형상으로 돌아간다. 원본 데이터와 DXF 내보내기는 단순화하지 않는다.

같은 넓은 축척에서 화면 후보 레이블은 LOD 2/3/4 공간창당 각각 최대 8/32/128개만 준비하고, 더 확대하면 전부 준비한다. 이는 레이블 텍스트·GEOS 앵커 계산과 보유량을 줄이는 화면 전용 정책이다. 원본 피처와 DXF 내보내기 레이블은 생략하지 않는다.

이 수치는 Go/native 객체의 실제 RSS 상한이 아니라 추정 payload 예산이다. 복제본, 공간 인덱스, 정점 버퍼, Qt 자원 때문에 RSS는 이보다 클 수 있다. 큰 화면이나 더 조밀한 데이터에서는 다른 안전 상한에 걸릴 수 있다. 따라서 실제 macOS 데이터에서 오류 소멸과 프로세스 RSS를 다시 확인하고, 전국 단위 자료에 대한 안전성 보장으로 해석하지 않는다.

세종시 연속지적도·지적도근점·건물 3개 실제 SHP의 parcel-fit 중심에서 약 1:52,716,
1600×1000 viewport를 테스트했다. 216개 공간창에서 91,313개 피처, 추정 payload
72.8 MiB, 4,418,355개 정점으로 완료됐으며 테스트 프로세스의 peak RSS는 279 MiB였다.
이 화면은 사용자 오류 로그의 정확한 중심·창 크기를 재현한 것은 아니며, GUI scenegraph의
메모리와 실제 사용자 화면의 완료 여부는 별도 확인이 필요하다.

같은 자료의 1:52,716 화면을 가상으로 4배 넓혀 1275개 공간창을 검사했을 때
220,300피처, 추정 payload 173.9 MiB, 9,310,845 정점으로 완료됐고 테스트
프로세스 peak RSS는 472 MiB였다. 필지·도근점 레이블을 켠 재검사에서는
화면 후보 1,837개, 추정 payload 174.0 MiB, peak RSS 481 MiB였고 31.64초에
완료됐다. 후보 제한 전에는 151,585개 레이블, 185.1 MiB, peak RSS 578 MiB,
약 60초였다. 이는 테스트용 viewport 확대이며 실제 모니터
해상도나 Qt GUI 메모리 측정이 아니다. 피처 수 상한은 300,000개지만 이 자료의
300,000피처 동시 렌더링을 입증한 결과도 아니다. 실제 가능량은 byte·정점 복잡도에 따라 달라진다.
